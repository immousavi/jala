پاسخت را با این شروع کن:

```
──────────── ⚡ OVERDRIVE ─────────────
》》》 Entering overdrive mode...
```

یک رابط را از مرزهای متعارف عبور بده. این فقط دربارهٔ افکت‌های بصری نیست. دربارهٔ استفاده از تمام قدرت مرورگر است تا هر بخشی از رابط فرا-معمول حس شود: جدولی که میلیون‌ها ردیف را هندل می‌کند، دیالوگی که از دکمهٔ فعال‌کننده‌اش متحول می‌شود، فرمی که با بازخورد streaming در لحظه اعتبارسنجی می‌کند، ترنزیشن صفحه‌ای که سینمایی حس شود.

بافت تصمیم می‌گیرد «فرا-معمول» یعنی چه. سیستم ذرات روی پورتفولیوی خلاقانه تأثیرگذار است. همان سیستم ذرات روی صفحهٔ تنظیمات، خجالت‌آور. ولی صفحهٔ تنظیماتی با ذخیره‌های خوش‌بینانهٔ فوری و ترنزیشن‌های حالتیِ انیمیت‌شده؟ آن هم فرا-معمول است. قبل از تصمیم‌گیری دربارهٔ مناسب، شخصیت و اهداف پروژه را بفهم.

### پیشنهاد قبل از ساختن

این فرمان بالاترین پتانسیل شلیکِ اشتباه را دارد. مستقیم وارد پیاده‌سازی نشو. باید:

1. **۲-۳ جهتِ متفاوت را فکر کنی**: تکنیک‌ها، سطوح بلندپروازی و رویکردهای زیبایی‌شناسی متفاوت را در نظر بگیر. برای هر جهت، کوتاه توصیف کن نتیجه چه شکلی می‌شود و چه حسی می‌دهد.
2. **قبل از نوشتن هر کدی انتخاب کاربر را بگیر.** با ابزار `question` بپرس و قبل از ادامه، منتظر پاسخ بمان. توصیفِ هر جهت و مصالحه‌هایش (پشتیبانی مرورگر، هزینهٔ کارایی، پیچیدگی) را داخل خود گزینه حمل کن، تا کاربر بین چیزهای قابل‌خواندن انتخاب می‌کند. سؤالِ ساختاریافته پیامی که درش سوار است را تا پاسخ کاربر قفل می‌کند، پس جهت‌هایی که کنار سؤال نوشته شده‌اند در حین انتخاب، نامرئی می‌مانند.
3. فقط با جهتی ادامه بده که کاربر تأییدش می‌کند.

رد‌شدن از این گام، ریسک ساختن چیزی خجالت‌آور است که باید دور انداخته شود.

### در مرورگر راستی‌آزمایی کن

افکت‌های بلندپروازانه به‌ندرت بار اول کار می‌کنند، پس آن‌ها را در مرورگر راستی‌آزمایی کن نه از روی کد: افکتی که فنی اجرا می‌شود می‌تواند همچنان تیکی باشد، غلط ease کند، یا روی فریم غلط فرود بیاید. چک‌ها را نشانه‌گیری کن روی زمان‌بندی، ایزینگ و نرمی، درست‌کرده‌ها را بین نگاه‌ها دسته‌ای بزن، و تا وقتی افکت فرا-معمول شود پالایش را ادامه بده.

## بسنج «فرا-معمول» اینجا یعنی چه

نوع درستِ بلندپروازی فنی کاملاً به آنچه با آن سر و کار داری بستگی دارد. قبل از انتخاب تکنیک بپرس: **چه چیزی کاربرِ همین رابطِ مشخص را می‌گوید «اوه، چه باحال»؟**

### برای سطح‌های بصری/بازاریابی
صفحه‌ها، بخش‌های هیرو، صفحه‌های فرود، پورتفولیوها: «اوه» اغلب حسی است: reveal اسکرول-رانده، پس‌زمینهٔ شیدر، ترنزیشن سینمایی صفحه، هنر مولدِ پاسخگو به نشانگر.

### برای UI کارکردی
جدول‌ها، فرم‌ها، دیالوگ‌ها، ناوبری: «اوه» در این است که چه حسی می‌دهد: دیالوگی که از طریق View Transitions از دکمه‌ای که فعالش کرده متحول می‌شود، جدول داده‌ای که با اسکرول مجازی ۱۰۰ هزار ردیف را با 60fps رندر می‌کند، فرمی با اعتبارسنجی streaming که آنی حس می‌شود، درگ‌ان‌دراپ با فیزیک فنری.

### برای UI حساس-به-کارایی
«اوه» نامرئی ولی محسوس است: جست‌وجویی که ۵۰ هزار آیتم را بدون فلیکر فیلتر می‌کند، فرم پیچیده‌ای که هرگز thread اصلی را مسدود نمی‌کند، ویرایشگر تصویری که نزدیک-به-زمان‌واقعی پردازش می‌کند. رابط فقط هیچ‌وقت تردید نمی‌کند.

### برای رابط‌های پر-داده
نمودارها و داشبوردها: «اوه» در روانی است: رندر شتاب‌یافته GPU با Canvas/WebGL برای داده‌های انبوه، ترنزیشن‌های انیمیت بین حالت‌های داده، چیدمان‌های گراف نیرو-جهت‌دار که طبیعی آرام می‌گیرند.

**رشتهٔ مشترک**: چیزی در پیاده‌سازی از آنچه کاربران از رابط وب انتظار دارند فراتر می‌رود. تکنیک به تجربه خدمت می‌کند، نه برعکس.

## جعبه‌ابزار

بر اساس آنچه می‌خواهی به دست آوری سازماندهی شده، نه بر اساس نام تکنولوژی.

### سینمایی‌کردن ترنزیشن‌ها
- **View Transitions API** (همان-سند: همهٔ مرورگرها؛ بین-سند: بدون فایرفاکس): متحول‌سازی عنصر مشترک بین حالت‌ها. آیتم فهرستی که به صفحهٔ جزئیات باز می‌شود. دکمه‌ای که به دیالوگ تبدیل می‌شود. نزدیک‌ترین چیز به انیمیشن‌های FLIP نیتیو.
- **`@starting-style`** (همهٔ مرورگرها): انیمیت عناصر از `display: none` به نمایان فقط با CSS، شامل keyframeهای ورود.
- **فیزیک فنری**: حرکت طبیعی با جرم، کشش و میرایی به‌جای cubic-bezier. کتابخانه‌ها: motion (Framer Motion قبلی)، GSAP، یا حل‌گر فنری خودت.

### گره‌زدن انیمیشن به موقعیت اسکرول
- **انیمیشن‌های scroll-driven** (`animation-timeline: scroll()`): فقط-CSS، بدون JS. Parallax، نوارهای پیشرفت، توالی‌های reveal — همه رانده از موقعیت اسکرول. (Chrome/Edge/Safari؛ فایرفاکس: فقط با فلگ؛ همیشه fallback ایستا بده)

### رندر فراتر از CSS
- **WebGL** (همهٔ مرورگرها): افکت‌های شیدر، پس‌پردازش، سیستم‌های ذرات. کتابخانه‌ها: Three.js، OGL (سبک)، regl. برای افکت‌هایی که CSS بیانشان نمی‌کند.
- **WebGPU** (Chrome/Edge؛ Safari 26+؛ فایرفاکس روی Windows/macOS؛ روی Firefox Linux/Android فقط فلگ): محاسبات GPU نسل بعد، قدرتمندتر از WebGL. همیشه به WebGL2 برگرد.
- **Canvas 2D / OffscreenCanvas**: رندر سفارشی، دست‌کاری پیکسل، یا بردنِ رندر سنگین کامل به بیرون thread اصلی با Web Workers + OffscreenCanvas.
- **زنجیره‌های فیلتر SVG**: نقشه‌های جابه‌جایی، آشفتگی، مورفولوژی برای افکت‌های اعوجاج ارگانیک. قابل-انیمیت با CSS.

### زنده‌کردن داده
- **اسکرول مجازی**: رندر فقط ردیف‌های نمایان برای جدول‌ها/فهرست‌ها با ده‌ها هزار آیتم. برای حالت‌های ساده کتابخانه لازم نیست؛ برای پیچیده‌ها TanStack Virtual.
- **نمودارهای شتاب‌یافته GPU**: بصری‌سازی داده با رندر Canvas یا WebGL برای مجموعه‌داده‌های بزرگ‌تر از SVG/DOM. کتابخانه‌ها: deck.gl، رندررهای سفارشی مبتنی بر regl.
- **ترنزیشن‌های انیمیت داده**: بین حالت‌های نمودار متحول شو به‌جای جایگزینی. `transition()` دالماسهٔ D3 یا View Transitions برای نمودارهای DOM-محور.

### انیمیت پراپرتی‌های پیچیده
- **`@property`** (همهٔ مرورگرها): ثبت پراپرتی‌های CSS سفارشی با نوع، فعال‌سازی انیمیشن گرادیان‌ها، رنگ‌ها و مقدارهای پیچیده‌ای که CSS معمولاً نمی‌تواند درون‌یابی کند.
- **Web Animations API** (همهٔ مرورگرها): انیمیشن‌های JavaScript-رانده با کارایی CSS. قابل‌ترکیب، قابل‌لغو، بازگشت‌پذیر. پایهٔ کُرئوگرافی پیچیده.

### هل‌دادن مرزهای کارایی
- **Web Workers**: انتقال محاسبات به بیرون thread اصلی. پردازش سنگین داده، دست‌کاری تصویر، ایندکس‌گذاری جست‌وجو: هرچیزی که jank می‌سازد.
- **OffscreenCanvas**: رندر در thread Worker. thread اصلی آزاد می‌ماند در حالی که بصری‌های پیچیده در پس‌زمینه رندر می‌شوند.
- **WASM**: کارایی نزدیک-به-نیتیو برای قابلیت‌های سنگین-محاسباتی. پردازش تصویر، شبیه‌سازی فیزیک، کدک‌ها.

### تعامل با دستگاه
- **Web Audio API**: صدای فضایی، بصری‌سازی‌های صدا-واکنش، بازخورد سونیک. برای شروع ژست کاربر می‌خواهد.
- **Device APIها**: جهت‌گیری، نور محیطی، جغرافیای مکانی. کم‌مصرف و همیشه با اجازهٔ کاربر.

**توجه**: این فرمان دربارهٔ بهبودِ «حسِ» رابط است، نه تغییر آنچه محصول انجام می‌دهد. افزودن همکاری هم‌زمان واقعی، پشتیبانی آفلاین یا قابلیت‌های backend جدید، تصمیم محصول است نه بهبود UI. تمرکز روی فرا-معمول‌کردنِ قابلیت‌های موجود.

## با نظم پیاده کن

### بهبود تدریجی غیرقابل‌مذاکره است

هر تکنیک باید نرم تخریب شود. تجربهٔ بدون بهبود همچنان باید خوب باشد.

```css
@supports (animation-timeline: scroll()) {
  .hero { animation-timeline: scroll(); }
}
```

```javascript
if ('gpu' in navigator) { /* WebGPU */ }
else if (canvas.getContext('webgl2')) { /* WebGL2 fallback */ }
/* CSS-only fallback must still look good */
```

### قواعد کارایی

- هدف 60fps. اگر زیر ۵۰ افتادی، ساده کن.
- منابع سنگین (contextهای WebGL، ماژول‌های WASM) را فقط نزدیک ویوپورت lazy-initialize کن.
- رندر خارج-ازنما را متوقف کن. آنچه نمی‌بینی را بکش.
- روی دستگاه‌های میان‌ردهٔ واقعی تست کن، نه فقط ماشین توسعه‌ات.

### پالایش، تفاوت را می‌سازد

فاصلهٔ بین «باحال» و «فرا-معمول» در ۲۰٪ آخرِ پالایش است: منحنی ایزینگِ انیمیشن فنری، آفست زمانیِ reveal پلکانی، حرکت ثانویهٔ ظریفی که ترنزیشن را فیزیکی حس می‌کند. اولین نسخه‌ای که کار کرد را عرضه نکن؛ نسخه‌ای را عرضه کن که اجتناب‌ناپذیر حس شود.

**هرگز**:
- افکت‌هایی عرضه نکن که روی دستگاه‌های میان‌رده jank می‌سازند
- APIهای تازه-و-خونین را بدون fallback کارا استفاده نکن
- بدون opt-in صریح کاربر صدا اضافه نکن
- بلندپروازی فنی را ماسکِ اصولِ ضعیفِ طراحی نکن؛ اول آن‌ها را با فرمان‌های دیگر درست کن
- چندین لحظهٔ فرا-معمولِ رقیب را روی هم نچین. فوکوس اثر می‌سازد، افراط نوفه

## نتیجه را راستی‌آزمایی کن

- **تست اوه**: به کسی نشانش بده که ندیده. واکنش نشان می‌دهد؟
- **تست حذف**: بردارش. تجربه کاسته می‌شود، یا کسی نمی‌فهمد؟
- **تست دستگاه**: روی موبایل، تبلت، کروم‌بوک اجراش کن. هنوز نرم است؟
- **تست بافت**: برای همین برند و مخاطب منطقی است؟

«فنی-فرا-معمول» دربارهٔ استفاده از جدیدترین API نیست. دربارهٔ این است که رابط کاری بکند که کاربران فکر می‌کردند وب‌سایت نمی‌تواند.
